# note の紹介記事を作る

リポジトリにある学校向けWebアプリについて、note の連載
「教室で使えるかもしれないもの作り」に載せる紹介記事を、実画面のスクリーンショットつきで作る。

納品物はこの3つ。

```
docs/note/
├── <app>-note-article.md   記事本文。そのまま note に貼れる形
├── images/                 実際に操作して撮った画面
└── README.md               入稿手順・画像の対応表・数字の出どころ・文体のメモ
```

## 進めかた

調査、撮影、執筆の順に進む。**撮影を先に済ませる**のが大事で、
撮っている最中に「実際はこう動く」「この機能は壊れている」が分かる。
先に文章を書くと、手もとの資料から想像で書いてしまい、事実と食いちがう。

### 1. アプリを読み解く

`README.md`、`MANUAL.md`（先生向けの手引きがあれば）、`package.json`、
`src/` の主要ファイルを読む。押さえるのは次のあたり。

- 何ができるアプリか。目玉はどれか
- 先生が知りたい制約。個人情報、通信、校内フィルタリングで許可が必要なアドレス、
  オフラインで動くか、共用端末での注意
- 記事に書く数字。コース数、問題数、種類の数、上限値

**数字は必ず実測かコードで裏を取る。** README は古くなっていることがある。
Qalc の回は README が「約11,800問」だったが、アプリのドリル一覧を数えたら 12,796 問だった。
数えられるものは、アプリを開いて数える。

裏を取った出どころは、あとで `docs/note/README.md` に一覧で残す。
書き手が「この数字どこから？」となったときに追えるようにするため。

過去の連載記事が手に入るなら読む。文体を合わせる材料になるし、
前作の紹介記事があれば「前作との差」が記事の推進力になる。

### 2. 画面を撮る

**先に `references/screenshots.md` を読む。** 踏んだ落とし穴が全部書いてある。
ふりがな入りボタンの照合、お祝いモーダルの回避、P2P のシグナリングサーバ、
URL の見た目、自動で解かせるときのペース。読まずに撮ると同じところで転ぶ。

土台は用意してある。

```bash
npm i --no-save playwright                                  # peer も要るなら一度にまとめて
npm run build
node <skill>/scripts/serve.mjs dist 4180 /<リポジトリ名>/     # 別ターミナル、または背景で
node <skill>/scripts/capture.mjs shots.mjs --base http://127.0.0.1:4180/<リポジトリ名>/ --out shots
```

`shots.mjs` は自分で書く。1台ぶんのブラウザを開いて、文字でボタンを押して、撮るだけ。

```js
export const viewport = { width: 390, height: 940 };

export default async ({ open, log }) => {
  const p = await open('main');
  await p.shot('01-home');
  log(await p.buttons());          // 次に何を押せるか分からないときはこれを見る

  await p.click('スコアアタック');
  await p.sleep(900);
  await p.click('3年');
  await p.shot('02-select');
};
```

複数端末が要るときは `open()` を人数ぶん呼ぶ。使える道具は
`click` `waitFor` `buttons` `text` `setInput` `setRange` `scrollTo` `resize` `sleep` `shot` `eval`。
詳しくは `scripts/capture.mjs` の冒頭のコメント。

進めかたのコツとして、いきなり全部を撮ろうとせず、
**1画面ずつ `buttons()` と `text()` を出して確かめながら進む。**
押せていないのに撮り続けると、違う画面が並んだことに最後まで気づけない。

撮る枚数は 15〜25 点くらい。ホーム、設定、動いているところ、結果、目玉の機能、
先生向けの設定画面。目玉の機能には多めに割く。

**撮影用のシナリオはリポジトリの中に置くことになる**（`node_modules` の解決の都合）。
`.tmp-shots/` のような分かる名前にして、納品前に必ず消す。

#### 撮っているあいだに、壊れている機能を見つけたら

記事より先にそれを報告する。動かない機能を紹介する記事を出すわけにいかない。
直せるなら直し、**記事とは別のコミットに分けて**、
「公開の前にこの修正を反映してください」と伝える。

撮影は、いちばん丁寧な受け入れテストでもある。そのつもりで踏む。

### 3. 記事を書く

**`references/style.md` を読んでから書く。** 連載の文体と構成、
そして守らないといけないルールが書いてある。とくにこの4つは外せない。

- 太字（`**`）、斜体、表を使わない。`→` `／` `▲` のような記号も使わない
- 箇条書きは手順のときだけ。あとは文章で書く
- 専門用語を日常の言葉に置きかえる
- 絵文字は見出しだけ

見出しは `🏫 はじめに` `📱 このアプリでできること` `✨ 導入のメリット`
`🛠️ 【管理者向け】導入手順` `📖 【利用者向け】使い方のガイド` `📝 まとめ` を基本にする。
目玉が収まらないときだけ、📱 と ✨ のあいだに2本まで足す。

**連載番号は推測で埋めない。** 分からなければ `#◯` のままにして、
納品時に「ここだけ直してください」と伝える。

書けたら、機械的に確かめられるところを確かめる。

```bash
python3 - <<'PY'
import re
s = open('docs/note/<app>-note-article.md', encoding='utf-8').read()
print('太字', s.count('**'), '／表', len([l for l in s.split('\n') if l.startswith('|')]))
for sym in ['→', '／', '▲', '▶']:
    print(sym, s.count(sym))
print('本文の字数', len(re.sub(r'!\[.*?\]\(.*?\)', '', s)))
PY
```

太字と表と記号が 0、字数が 7,000〜9,000 なら形は整っている。
参照している画像がすべて実在するかも確かめる。

### 4. 納品する

`docs/note/README.md` に、書き手が次に何をすればいいかを書く。

- note に貼る手順。タイトル行、画像の手動アップロード、キャプション欄、ハッシュタグ欄
- 貼るまえに直すところ（連載番号など）
- 画像の一覧。ファイル名、何の画面か、本文のどこで使うか
- 記事に書いた数字の出どころ
- 撮り直すときの手順
- 文体について何を踏襲したか

記事と修正は別のコミットに分ける。書き手が修正だけ先に出せるようにするため。
撮影のために一時的に当てた変更（接続先の差しかえ、CSP、`/etc/hosts`）が
差分に残っていないか、`git status` と `git diff` で必ず確かめる。

## 手を出さないこと

- **教室での出来事を実体験として書かない。** これは作者の実践記録ではないので、
  「使ってみたら子どもたちが〜」と書くと嘘になる。「こうなればいいと思って作った」まで
- **効果を言い切らない。** 「いちばん盛り上がる時間になる」ではなく「〜だと思います」
- **裏の取れていない数字を書かない。** 数えられるものは数える
- **スクリーンショットを加工・合成しない。** 実際に操作して撮ったものだけを使う
